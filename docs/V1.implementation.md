# Checkless V1 Implementation Blueprint

## Purpose

This document is the implementation handoff for moving Checkless from an
anonymous, memory-only prototype to an account-backed multiplayer platform. It
records the product decisions, data contracts, invariants, and atomic delivery
order agreed for V1.

The work must be delivered one atomic feature at a time. Do not combine all
phases into one large change. Each phase must leave the existing game playable,
include its own verification, and be safe to deploy before the next phase is
started.

The database schema is defined in `backend/prisma/schema.prisma`. The schema is
created in the first atomic phase, but no database migration should be applied
until it has been reviewed and approved.

## Product Definition

Checkless is simultaneous chess:

- White and black do not take turns.
- Each player has an independent cooldown of 1, 3, or 5 seconds.
- A player may move whenever their cooldown reaches zero.
- The backend remains authoritative for move validation, ordering, board state,
  and cooldowns.
- Check and checkmate do not exist. Capturing the opposing king wins.
- Socket.IO events are processed sequentially by the Node.js server, so even
  moves received very close together have one authoritative order.
- Historical replay must reproduce that server order and timing; standard PGN
  alone is not sufficient.

The existing engine is the V1 rules authority. Persistence work must not
silently alter movement rules. Every game stores `rulesVersion = 1` so future
engine corrections can coexist with old replays.

## Agreed V1 Product Rules

### Identity and access

- Clerk provides authentication and owns passwords, login providers, sessions,
  and session-token lifecycle.
- The application database owns usernames used for search, public profiles,
  roles, moderation status, friendships, ratings, and game history.
- Clerk usernames are enabled and mirrored into `User.username`.
- `normalizedUsername` is the lowercase form and is the authoritative unique
  lookup key.
- Casual matchmaking permits authenticated users and guests.
- Ranked matchmaking, friends, challenges, tournament participation, and admin
  operations require an authenticated human user.
- The product does not expose account deletion. Logout only ends the Clerk
  session. Historical users and games are never physically deleted.
- If a Clerk identity is removed administratively, mark `clerkDeletedAt` and
  retain the local user and historical relationships.

### Roles and bots

- Permission and identity type are separate concepts.
- `User.role` is `PLAYER` or `ADMIN`.
- `User.kind` is `HUMAN` or `BOT`.
- A human admin can still play games.
- Bot profiles exist in the V1 schema only. Bot engines and matchmaking are
  deferred.
- Deferred bot requirement: casual matchmaking may fill an unmatched seat with
  a bot after 30 seconds. Bot disclosure behavior was intentionally deferred
  with the rest of bot implementation and must be revisited before release.

### Public games

- All games are public, including direct challenges and tournament games.
- Anyone, including a guest, may watch a live game through read-only spectator
  events.
- Anyone may open a completed game and replay its accepted moves.
- “Challenge” means a direct two-player game created by code or friend invite;
  it does not make the game record private.
- Direct challenges are always unrated and expire if not accepted within 15
  minutes.

### Presence and reconnection

- Live presence, socket IDs, queue membership, timers, and reconnect deadlines
  are ephemeral state. Do not write timer ticks or socket IDs to PostgreSQL.
- Presence is visible only to accepted friends.
- Persist only throttled durable presence such as `lastSeenAt`.
- A disconnected player has 10 seconds to reclaim the same game seat.
- The game does not pause during that window. The opponent and both cooldowns
  continue normally, and the connected opponent may keep moving.
- If the king is captured during the reconnect window, king capture is the
  final result.
- Otherwise, expiry of the 10-second deadline causes
  `DISCONNECT_FORFEIT` against the disconnected player.
- A new socket may reclaim a seat only when its verified Clerk user ID or signed
  guest identity matches the original participant.

### Ratings

- Ratings are separate for 1-second, 3-second, and 5-second variants.
- Each rating starts at 1200.
- V1 uses integer Elo with K-factor 32.
- Expected score is `1 / (1 + 10 ** ((opponent - player) / 400))`.
- The new value is `round(old + 32 * (actual - expected))`.
- Apply both players' changes in the same database transaction.
- Public ranked matchmaking is rated.
- Casual and direct-challenge games are unrated.
- Tournaments are schema-ready for a host-selected rated flag. Tournament
  rating eligibility and anti-farming rules must be specified before tournament
  implementation.
- `ABORTED`, `SERVER_INTERRUPTED`, and `ADMIN_TERMINATED` games never change Elo.
- A resignation or disconnect forfeit after a ranked game starts is a rated
  loss.

## Schema Responsibilities

### `User`

Stores the durable application identity. `clerkUserId` is nullable so future
bot users and externally removed Clerk identities can be retained. A normal
active human must have a Clerk ID; enforce this in the identity service.

Never authorize an admin action from client-provided metadata. Resolve the
verified Clerk subject to `User` and use the local `role` and `status` fields.
Suspended users may read public pages but cannot queue, challenge, join a
tournament, or submit moves.

### `GuestIdentity`

Represents a stable anonymous browser identity. The backend issues a signed,
opaque guest token containing the guest ID and token version. Never use a socket
ID as identity and never store an unsigned guest ID supplied by the client.

Guests receive a stable public alias such as `Guest-A7K2`. Guest games are
persisted, but V1 does not provide a guest history page and does not merge guest
games into a later Clerk account.

### `BotProfile`

Provides future engine metadata without mixing it into human profiles. A
`BotProfile` may exist only for a `User` whose kind is `BOT`; enforce that in the
bot repository. `enabled` must be checked before a bot is eligible for future
matchmaking.

### `Game`

Represents one started match. Queue entries are not games. Create the `Game` and
its two participants in one transaction immediately before emitting
`game_start`.

`rated` is copied onto the game when it starts and never inferred later from
mode or tournament settings. `lastSequence` records the highest durably appended
move. Completed public game lists order by `endedAt DESC, id DESC` and use cursor
pagination.

### `GameParticipant`

There must be exactly two rows, one `WHITE` and one `BLACK`, before a game is
announced. Each row references exactly one identity source:

- authenticated human or bot: `userId` is set and `guestIdentityId` is null;
- anonymous player: `guestIdentityId` is set and `userId` is null.

The nullable relations allow historical snapshots to survive exceptional
identity removal. `usernameSnapshot`, display name, and avatar are immutable
after game start. Rating snapshots are populated only for rated games.

### `GameMove`

Contains accepted moves only. Rejected moves and premoves that become invalid
are not game history.

`sequence` starts at 1 and increments once per accepted move, regardless of
color. `acceptedAt` is server time. `elapsedMs` is measured from `Game.startedAt`.
Cooldown values are the authoritative values immediately after the move. Save
`fenAfter` for deterministic replay and resilience to later engine changes.

Clients should send a UUID `clientMoveId`. A repeated `(gameId, clientMoveId)`
must return the already accepted result rather than execute twice. The unique
sequence and client ID constraints are the final defense against duplicate
writes.

### `PlayerVariantStats`

Stores profile-ready computed values per user and variant. Update totals exactly
once during game finalization. `totalGames` includes every completed game with a
winner; ranked counters include only rated games. Games ending without a result
do not increment wins or losses.

The finalization service must be idempotent. It should first conditionally move
the game from `ACTIVE` to its terminal state, then update participants, ratings,
and statistics in the same transaction. If the game is already terminal, return
the stored result without updating counters again.

### Friends and blocks

`FriendRequest` stores one directional request pair and may be reused when a
declined or canceled request is sent again. The sender and receiver cannot be
the same user.

When accepting a request:

1. Verify it is still pending and neither user blocks the other.
2. Sort the two internal user IDs lexically.
3. Create `Friendship(userAId, userBId)` using that canonical order.
4. Mark the request accepted in the same transaction.

Blocking is directional. Creating a block must remove any friendship and cancel
pending requests and challenges between the two users in one transaction.

### `Challenge`

A challenge is signed-in-only and always produces a public, unrated game. The
host chooses one of the three variants. `opponentId` is populated immediately
for a direct friend invite or when another authenticated user claims a code.

Only an `OPEN`, unexpired challenge can be accepted. Acceptance must atomically
claim the empty opponent seat. Starting creates the game and changes the
challenge to `STARTED`; completion links to the final public game. Codes must be
generated with cryptographically secure randomness and compared case
insensitively at the API boundary.

### Tournament models

Tournament tables are intentionally included now but tournament code is not a
V1 implementation dependency.

- Any authenticated user may host.
- Access is public listing or code-based.
- The host chooses round-robin or Swiss.
- Arbitrary capacities such as 10 or 12 are supported through `maxPlayers`.
- `TournamentParticipant` stores registration, seed, score, tie-break score,
  and final rank.
- `TournamentRound` groups pairings by round number.
- `TournamentPairing` supports two players or a one-player bye and may link to
  exactly one public `Game`.
- `settings` stores format-specific policy that has not yet been finalized;
  future code must validate it by format rather than accepting arbitrary client
  JSON.
- `TournamentInvite` provides friend invitations in addition to public/code
  discovery.

Do not implement pairing algorithms from this document alone. Before that
phase, specify Swiss pairing, tie-break, scoring, color-balancing, withdrawal,
and rated-tournament anti-abuse policies.

### `AdminAuditLog`

Every moderation mutation requires a non-empty reason and audit row. Audit
entries are append-only. V1 admin scope is searching users, suspending/restoring
users, and inspecting games/replays. Never expose audit metadata on public
profiles.

## Database Invariants

Prisma expresses uniqueness and relations, but these rules must also be checked
by repository/service code. Add PostgreSQL `CHECK` constraints in the reviewed
migration where practical.

- `normalizedUsername = lower(username)`.
- Human users normally have `clerkUserId`; bots never require one.
- Bot profiles belong only to bot users.
- Self friend requests, friendships, and blocks are forbidden.
- Friendship IDs are stored in lexical canonical order and satisfy
  `userAId < userBId`.
- A game has exactly two participants with different colors.
- A participant has exactly one identity source at game creation.
- A participant can appear only once per game.
- A move's participant belongs to the same game as the move.
- Move sequences are positive and contiguous for each game.
- Cooldowns and elapsed time are non-negative.
- Completed games have `endedAt`, `finalFen`, and an end reason.
- A winning game has one winning participant matching `winnerColor`.
- Rated games contain two authenticated human participants.
- Challenges expire 15 minutes after creation and are never rated.
- Tournament capacity is at least two; round and board numbers are positive.
- A pairing cannot use the same tournament participant twice.
- A pairing's participants belong to the pairing's tournament.
- A bye has exactly one participant and no game.

## Runtime Architecture

### Durable versus ephemeral state

PostgreSQL stores users, social relationships, started games, accepted moves,
results, ratings, challenges, tournament structure, and audit records.

The current Node.js process continues to own live board objects, cooldowns,
premoves, matchmaking queues, active socket mappings, presence, and reconnect
deadlines. Introduce Redis and the Socket.IO Redis adapter only when running more
than one backend instance; do not pretend PostgreSQL is a low-latency presence
store.

### Ordered move persistence

Database latency must not delay board feedback. Each active game owns a promise
chain or equivalent single-consumer write queue:

1. Validate and apply the move to the authoritative in-memory engine.
2. Allocate the next monotonic sequence.
3. Emit `move_made` immediately with that sequence.
4. Enqueue the `GameMove` insert and `Game.lastSequence` update in order.
5. Record and surface persistence failures; never reorder later writes.
6. Before final settlement, await all queued move writes.
7. Finalize the game, participants, stats, and ratings transactionally.

If the process crashes, startup recovery marks database games still `ACTIVE` as
`INTERRUPTED` with `SERVER_INTERRUPTED`. These games remain public but unrated.
The architecture does not promise cross-process live-game recovery in V1.

## Planned API and Socket Contracts

These contracts belong to later atomic phases. Names may be added without
breaking existing anonymous casual clients, but authenticated operations must
never trust a user ID supplied in an event payload.

### REST resources

- `GET /api/me`: local authenticated profile, role, status, and ratings.
- `GET /api/users/search?q=&cursor=`: username search excluding blocked users.
- `GET /api/users/:username`: public profile and per-variant stats.
- `GET /api/users/:username/games?cursor=`: public completed games.
- `GET /api/games/:gameId`: public game summary and participants.
- `GET /api/games/:gameId/moves?cursor=`: ordered public replay data.
- Friend-request endpoints for list, send, accept, decline, and cancel.
- Friendship endpoints for list and remove.
- Block endpoints for list, create, and remove.
- Challenge endpoints for create, inspect by code, accept, cancel, and expire.
- Ranked/casual queue mutation stays on Socket.IO.
- Admin endpoints require local `ADMIN` role and create audit rows.

All collection endpoints use cursor pagination and bounded page sizes. Do not
return Clerk IDs, guest IDs, moderation reasons, or internal identity tokens in
public responses.

### Socket authentication

The frontend supplies a Clerk session token through Socket.IO `auth` when
signed in, otherwise a signed guest token. The server verifies the token during
the handshake and attaches an immutable identity object to `socket.data`.

Never accept `userId`, role, rating, or participant color from the client as an
authorization fact. Color is resolved from the active game membership.

### New and extended events

- Extend `find_game` with `mode`; variant remains required. Guests may request
  only `CASUAL`.
- Include public participant snapshots and move sequence in `game_start` and
  `move_made`.
- Add `spectate_game { gameId }`, which joins a read-only Socket.IO room and
  returns current FEN, timers, participants, last sequence, and status.
- Add `leave_spectating { gameId }`.
- Add reconnect success/failure events without pausing the live game.
- Add friend presence events only to sockets belonging to accepted friends.

Spectator sockets can receive game state, timer updates, moves, and game-over
events. They cannot call participant-only move, abort, resignation, or reconnect
operations.

## Atomic Delivery Plan

### Phase 1 — Schema and blueprint

- Replace the placeholder Prisma game model with the complete schema.
- Add this implementation blueprint.
- Run Prisma format, validation, and client generation.
- Do not apply a migration or connect feature code yet.

Acceptance: Prisma accepts all models and relations, generated client types are
available, and the live application behavior is unchanged.

### Phase 2 — Clerk and guest identity

Status: authenticated-human login and play are implemented. Guest identity is
still deferred, so the current `/play` route and Socket.IO server require a
verified Clerk session.

- Add Clerk React and Express integrations.
- Add verified optional Socket.IO authentication.
- Synchronize users idempotently on authenticated access and Clerk webhooks.
- Issue and verify guest tokens.
- Reject suspended identities from mutations.
- Throttle `lastSeenAt` writes.

Acceptance: refreshes and socket reconnects preserve identity; forged tokens,
client roles, and client user IDs cannot impersonate another player.

Current implementation notes:

- The frontend uses `@clerk/react`, dedicated `/sign-in` and `/sign-up` routes,
  and Clerk controls in the shared header.
- The Socket.IO client requests a current Clerk session token for every
  connection attempt rather than caching a token in local storage.
- The server verifies the token and authorized frontend origin before running
  any game event handler.
- The local `User` row is upserted from Clerk during the authenticated socket
  handshake. Local role and suspension state remain database-controlled.
- The same synchronization disables Clerk self-deletion for the user, matching
  the product rule that accounts may log out but cannot delete their history.
- Guest play must be reintroduced as a separate explicit auth path; never make
  the authenticated middleware silently accept missing tokens.

### Phase 3 — Game persistence and reconnect

- Create games/participants transactionally at match start.
- Add monotonic sequence and client move IDs.
- Persist moves through per-game ordered queues.
- Finalize every king capture, abort, resignation, disconnect forfeit, and
  server interruption idempotently.
- Replace immediate disconnect loss with the agreed live 10-second reclaim
  window without pausing gameplay.

Acceptance: completed casual games survive restart and replay in exact sequence;
repeated finalization cannot duplicate stats; an opponent can continue moving
during another player's reconnect window.

### Phase 4 — Public history, replay, and spectating

- Build public profile, history, game detail, and replay APIs/pages.
- Replay from `initialFen` through ordered moves using server elapsed time.
- Add public read-only live spectating.
- Ensure spectators cannot mutate a game or see secret identity data.

Acceptance: guest and authenticated viewers can watch and replay any game;
historical profile snapshots remain unchanged after profile edits.

### Phase 5 — Friends, blocks, and challenges

- Implement username search, requests, accepted friendships, removal, and
  blocking transactions.
- Broadcast presence only to accepted, non-blocked friends.
- Implement public, unrated challenges via friend invite or short code.
- Expire unused challenges after 15 minutes.

Acceptance: duplicate/reverse friendships cannot exist, block enforcement is
bidirectional for interaction, and only one user can atomically claim a code.

### Phase 6 — Ranked and statistics

- Add authenticated-human-only queues per variant.
- Match within a rating window that expands while waiting.
- Apply K=32 Elo and all statistics once in the finalization transaction.
- Exclude challenges, casual games, bots, and no-result endings from Elo.

Acceptance: concurrent or duplicate finalization cannot award rating twice and
the sum of both rounded rating deltas stays as close to zero as independent
rounding permits.

### Phase 7 — Admin moderation

- Add protected user/game search.
- Implement suspend and restore operations with mandatory reasons.
- Append audit records for every mutation.
- Disconnect newly suspended users from queues and prevent new moves.

Acceptance: non-admins cannot access operations, audit records are append-only,
and suspension never deletes public history.

### Phase 8 — Tournaments (deferred)

- First finalize Swiss/round-robin scoring, pairing, tie-break, withdrawal,
  color, and rated-game policies.
- Then implement creation, public/code registration, invites, rounds, pairings,
  public tournament pages, and progression.

### Phase 9 — Bots (deferred)

- Select and version a bot engine.
- Route bot moves through the same validation, sequencing, persistence, and
  participant pipeline as human moves.
- Reconfirm bot disclosure policy before release.
- Add the deferred 30-second casual fallback only after load and fairness tests.

## Phase 1 Verification

Run from `backend`:

```bash
npx prisma format
npx prisma validate
npx prisma generate
```

Do not run `prisma db push`, `prisma migrate dev`, or manually alter Neon during
Phase 1. After schema approval, create a named migration, review its SQL, add
database check constraints not expressible by Prisma, test it against a fresh
database, and only then apply it to the target environment.

## Explicit Non-Goals for This Change

- No Clerk packages or UI.
- No REST endpoints.
- No Socket.IO event changes.
- No live-game behavior changes.
- No migration application or data backfill.
- No Redis deployment.
- No tournament pairing implementation.
- No bot engine or bot matchmaking.
